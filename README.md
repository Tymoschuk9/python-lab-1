# Опис алгоритму та архітектури проєкту

Для виконання лабораторної роботи було обрано **Варіант №4 (Система банківських рахунків)**. 

### 1. Структура проєкту (`src-layout`)
Проєкт організовано відповідно до сучасних стандартів розробки на Python із використанням структури `src-layout`. Це дозволяє уникнути випадкових імпортів неінстальованого коду та полегшує тестування і збирання пакета.

```text
bank_system/
│
├── pyproject.toml
├── README.md
├── .gitignore
│
├── src/
│   └── bank_system/
│       ├── __init__.py
│       ├── exceptions.py
│       ├── models.py
│       ├── services.py
│       └── main.py
└── .venv/
```

### 2. Розподіл на модулі та архітектурні шари
Програма розділена на 4 логічні модулі в пакеті `bank_system`:

*   **`exceptions.py` (Власні винятки):**
    Містить ієрархію винятків для обробки помилок предметної області. Базовим класом є `BankError`. Наслідники: `InsufficientFundsError` (недостатньо грошей для зняття), `InvalidAmountError` (некоректна сума введення), `AccountNotFoundError` (рахунок не знайдено).
*   **`models.py` (Модель даних):**
    Використовує декоратор `@dataclass` для створення моделі `Account` (клієнт, номер рахунку, поточний баланс). Усередині dataclass реалізовано методи бізнес-валідації `deposit()` та `withdraw()`. Якщо баланс після списання стає меншим за нуль, піднімається виняток `InsufficientFundsError`, що гарантує цілісність даних і унеможливлює від'ємний баланс.
*   **`services.py` (Сервісний шар / Бізнес-логіка):**
    Клас `BankService` інкапсулює роботу з колекцією рахунків (імітація бази даних). Реалізує методи:
    *   `create_account()`: створення рахунку з перевіркою унікальності його номера та дотриманням ліміту початкового внеску (використовує константу конфігурації `MIN_INITIAL_DEPOSIT`).
    *   `find_account()` та `find_account_silent()`: пошук рахунку за номером із генерацією помилок або поверненням `None`.
    *   `search_by_client_name()`: регістронезалежний пошук рахунків клієнтів за фрагментом імені.
    *   `get_total_bank_funds()`: агрегація загальної суми коштів усіх рахунків банку.
    *   `get_all_accounts()`: отримання списку всіх рахунків із підтримкою сортування за алфавітом або сумою балансу.
*   **`main.py` (Точка входу та користувацький інтерфейс):**
    Керує взаємодією з користувачем через консольне меню (`menu-driven interface`), виконує первинне наповнення демо-даними (`seed_demo_data`) та забезпечує надійну валідацію введених даних користувачем (наприклад, перехоплення `ValueError` при введенні тексту замість чисел).

### 3. Опис алгоритмів бізнес-операцій

*   **Алгоритм списання коштів з перевіркою балансу:**
    ```mermaid
    graph TD
        A[Запит суми списання] --> B{Чи сума > 0?}
        B -- Ні --> C[Помилка InvalidAmountError]
        B -- Так --> D{Баланс - Сума >= 0?}
        D -- Ні --> E[Помилка InsufficientFundsError]
        D -- Так --> F[Зменшити баланс на суму]
    ```
*   **Регістронезалежний пошук:**
    Користувач вводить запит `query`. Програма перетворює його в нижній регістр та порівнює з кожним ім'ям клієнта через оператор `in` (наприклад, `query.lower() in acc.client_name.lower()`), що дозволяє знаходити записи за частиною прізвища чи імені незалежно від розкладки клавіатури та регістру.

# Опис конфігураційних файлів проєкту

### 1. Файл `pyproject.toml`
Конфігураційний файл проєкту описує метадані згідно з сучасним стандартом **PEP 518/621** та визначає механізм автоматичного запуску консольної команди:

```toml
[build-system]
requires = ["setuptools>=70"]
build-backend = "setuptools.build_meta"

[project]
name = "bank-system"
version = "0.1.0"
description = "Система банківських рахунків - Лабораторна робота 1"
requires-python = ">=3.11"
authors = [
    { name = "Студент", email = "student@univ.edu.ua" }
]
classifiers = [
    "Programming Language :: Python :: 3",
    "Operating System :: OS Independent",
]

[project.scripts]
bank-system = "bank_system.main:main"
```

### 2. Файл `.gitignore`
Запобігає потраплянню службових та тимчасових файлів до Git-репозиторію.
```text
.venv/
__pycache__/
*.pyc
.pytest_cache/
.idea/
.vscode/
dist/
build/
*.egg-info/
.env
```

### 3. Фрагмент файлу `README.md`
```markdown
# Bank System

Консольний застосунок для управління банківськими рахунками. 
Виконано в межах лабораторної роботи №1 з дисципліни «Професійний Python».

## Встановлення

1. Створіть та активуйте віртуальне середовище:
   ```bash

   source .venv/bin/activate  # На Windows: .venv\Scripts\activate
   ```
2. Встановіть проєкт у режимі редагування (editable mode):
   ```bash
   python -m pip install -e .
   ```

## Запуск програми

Ви можете запустити застосунок як модуль:
```bash
python -m bank_system.main
```
Або через зареєстровану консольну утиліту:
```bash
bank-system

# Відповіді на контрольні запитання

1.  **Що таке Python-проєкт?**  
    Це структурована сукупність вихідного коду, метаданих, конфігураційних файлів, тестів та документації, призначена для вирішення певного кола завдань та готова до розгортання або публікації.
2.  **Чим проєкт відрізняється від одного Python script?**  
    Проєкт складається з багатьох взаємопов'язаних модулів (пакетів), має чітко визначену структуру (наприклад, `src-layout`), інструкції зі встановлення (`pyproject.toml`), ізольовані залежності (`venv`) та систему контролю версій. Скрипт — це один автономний файл `.py`.
3.  **Що таке Python module?**  
    Це окремий файл із розширенням `.py`, який містить визначення функцій, класів та змінних, що можуть бути імпортовані в інші модулі.
4.  **Що таке Python package?**  
    Це каталог, що містить файли модулів та спеціальний файл `__init__.py`. Пакети дозволяють ієрархічно структурувати простір імен.
5.  **Для чого потрібний `__init__.py`?**  
    Він вказує інтерпретатору Python, що каталог є пакетом. Також у ньому можна визначати рівень експорту об'єктів пакета (змінна `__all__`) та метадані типу `__version__`.
6.  **Що таке `src-layout`?**  
    Це підхід до організації файлової структури, за якого весь продуктовий код застосунку розміщується у виділеній підпапці `src/` (наприклад, `src/my_package/...`), а тести та метадані — в корені проєкту.
7.  **Які переваги має `src-layout`?**  
    Він запобігає випадковому імпорту локального коду (який не був інстальований у віртуальне середовище), гарантує відповідність тестованого коду тому, що буде зібраний у дистрибутив, і робить структуру проєкту більш зрозумілою.
8.  **Для чого використовується virtual environment?**  
    Для ізоляції залежностей (бібліотек та версій Python) конкретного проєкту від глобальної системи та інших проєктів на комп'ютері, уникаючи конфлікту версій.
9.  **Як створити `.venv`?**  
    За допомогою вбудованої команди: `python -m venv .venv`
10. **Як активувати virtual environment?**  
    *   Linux/macOS: `source .venv/bin/activate`
    *   Windows (CMD): `.venv\Scripts\activate.bat` або PowerShell: `.venv\Scripts\Activate.ps1`
11. **Для чого використовується pip?**  
    Це менеджер пакетів для Python, який використовується для встановлення, оновлення та видалення зовнішніх бібліотек із репозиторію PyPI або локальних джерел.
12. **Чому рекомендується `python -m pip` замість просто `pip`?**  
    Це гарантує використання саме тієї версії `pip`, яка жорстко прив'язана до обраного інтерпретатора Python (особливо актуально за наявності кількох версій Python у системі).
13. **Для чого потрібний `pyproject.toml`?**  
    Це єдиний уніфікований конфігураційний файл для інструментів розробки Python (заміна старіших `setup.py`, `setup.cfg`). Він містить метадані проєкту, описує залежності та вказує build-систему (наприклад, setuptools, poetry, hatch).
14. **Що містить секція `[project]`?**  
    Загальні метадані проєкту: ім'я, версію, опис, контакти авторів, мінімально необхідну версію Python, залежності та консольні скрипти для запуску.
15. **Що таке `editable installation`?**  
    Це режим встановлення пакета (`pip install -e .`), за якого зміни у вихідному коді в каталозі розробки миттєво відображаються в роботі інстальованого пакета без необхідності його повторного перевстановлення.
16. **Для чого використовується `if __name__ == "__main__":`?**  
    Ця конструкція гарантує, що код всередині цього блоку виконається лише у разі безпосереднього запуску файлу як скрипта, але не виконається при його імпортуванні в інші модулі.
17. **Що таке Git?**  
    Це розподілена система контролю версій, яка відстежує зміни у файлах проєкту, дозволяє повертатися до попередніх станів та організовує спільну роботу розробників.
18. **Що таке repository?**  
    Це сховище (база даних Git), де зберігається історія змін файлів проєкту, комміти, гілки та метадані.
19. **Що таке commit?**  
    Це зафіксований знімок (snapshot) стану файлів проєкту на певний момент часу з унікальним ідентифікатором (хешем) та коментарем розробника.
20. **Для чого використовується `git status`?**  
    Для відображення поточного стану робочої директорії: які файли змінено, які підготовлено до комміту (staged), а які ще не відстежуються Git (untracked).
21. **Для чого `git add`?**  
    Для перенесення змін із робочої директорії до індексу (staging area) — підготовка файлів до наступного комміту.
22. **Для чого `git commit`?**  
    Для збереження підготовлених змін з індексу в локальну історію репозиторію з описом виконаної роботи.
23. **Що показує `git log`?**  
    Історію всіх коммітів у поточній гілці із зазначенням авторів, дат та описів змін у хронологічному порядку.
24. **Для чого потрібен `.gitignore`?**  
    Для зазначення шаблонів шляхів та файлів, які Git повинен ігнорувати і ніколи не додавати до репозиторію (наприклад, паролі, файли конфігурації IDE, віртуальні середовища).
25. **Чому `.venv` не потрібно комітити?**  
    Тому що папка містить тисячі бінарних системних файлів, які легко генеруються на будь-якому іншому ПК однією командою із конфігураційного файлу. Зберігання `.venv` у Git значно збільшує розмір репозиторію та порушує кросплатформеність.
26. **Для чого потрібний `README`?**  
    Він є точкою входу для користувачів та розробників; містить опис проєкту, інструкції зі встановлення, налаштування та запуску застосунку.
27. **Що таке `type hints`?**  
    Це механізм анотації типів даних у коді Python (наприклад, `amount: float`), який полегшує розуміння коду розробниками, допомагає IDE підказувати методи та дозволяє проводити статичний аналіз коду (за допомогою інструментів на кшталт `mypy`).
28. **Для чого програму розділяють на modules?**  
    Для покращення читабельності коду, спрощення тестування та відладки, можливості повторного використання окремих блоків та структурування великих проєктів за принципом розділення відповідальності (Separation of Concerns).
29. **Що таке `business logic`?**  
    Це ядро програми, правила та алгоритми обробки даних, які описують реальні процеси предметної області (наприклад, правила нарахування відсотків, проведення транзакцій, недопущення від'ємного балансу), незалежно від інтерфейсу користувача чи способу збереження даних.
30. **Чому потрібно відокремлювати `application entry point` від `business logic`?**  
    Це робить бізнес-логіку незалежною від представлення. Завдяки цьому ми можемо легко змінити інтерфейс програми з консольного на графічний (GUI) чи веб-сервіс (API), взагалі не змінюючи логіку роботи з банківськими рахунками.

# Висновок
У ході лабораторної роботи було успішно здійснено перехід від написання простих скриптів до професійної організації Python-проєкту.

Було набуто практичних навичок роботи з ізольованим віртуальним середовищем `.venv` та інструментом `pip`. Застосування структури проєкту `src-layout` спільно з конфігуруванням метаданих через `pyproject.toml` дало змогу створити повноцінний пакет, який легко інсталюється в систему за допомогою команди `pip install -e .` та запускається через створену консольну утиліту `bank-system`.

Реалізація індивідуального варіанта №4 продемонструвала переваги об'єктно-орієнтованого підходу та використання dataclass для моделювання сутностей предметної області. Розділення програми на модулі (`models.py`, `services.py`, `exceptions.py`, `main.py`) дозволило ізолювати бізнес-логіку перевірки лімітів та операцій з балансом від інтерфейсу взаємодії з користувачем. Також було застосовано систему контролю версій Git для ведення історії розробки відповідно до логічних етапів. Отриманий каркас проєкту є надійним фундаментом для подальшого розширення та вивчення просунутих можливостей мови Python.
